# 目标效果评测（倒计时）：维度、扣分规则与计算口径

本文按当前代码实际行为整理，供规则复核使用。对应实现：`target-effect` 插件 1.4.0、rubric v4、规范 profile `countdown-card-spec-v1`。

结论先行：评测只消费浏览器采集到的确定性证据，模型不参与判定；总分由「目标语义 25 + 可见性 37.5 + 规范符合 37.5」三个维度直接相加，**固定构成 100 分**，待复核按半通过计分，L0 失败直接 0 分。不适用维度记 0 分并展示原因，不再收缩分母，所以页面上三个维度分相加就是总分。**mock 设备时间推导出的期望只展示、不计目标分**，因此当前不加 `expectations.json` 时，目标语义为 0/25，总分等于可见性与规范的实际得分。权重自 2026-11-11 起由 40/25/25 调整为 25/37.5/37.5：目标语义问题较少，把分值更多留给可见性与规范符合。

## 一、总分计算

### 1.1 维度与权重

| 维度 | 权重 | 何时适用 | 说明 |
|---|---|---|---|
| 目标语义（target） | 25 | 期望值来自数据集作者的**显式声明**（`provenance` 为 `explicit`） | 不适用时记 0 分并展示原因；由 mock 设备时间推导的期望只作参考 |
| 可见性（visibility） | 37.5 | 采集到 DOM/截图证据 | 只看 Web 渲染结果，不推断业务语义；不适用的样本记 0 分 |
| 规范符合（spec） | 37.5 | 存在参与计分的 `SPEC.*` 规则 | 非 Pixso 主题的样本记 0 分并展示原因，见 §5.2 的口径问题 |

### 1.2 单条规则如何折算

每个维度内部**规则等权**：

```text
适用规则集合 = 该维度下状态为 pass / fail / pending 的规则
               （na、未产出的规则不计入分母）

规则状态取值：pass = 1.0，pending = 0.5，fail = 0.0
同一规则出现多条结果时，取这些取值的算术平均

维度通过率 ratio = Σ规则取值 ÷ 适用规则数
维度得分 score = round(维度权重 × ratio, 1)
单条规则满分 unit = 维度权重 ÷ 适用规则数
单条扣分 deduction = round(unit × (1 − 规则取值), 1)
```

关键后果：**单条规则的满分不是固定的**，取决于该样本这一维实际适用了多少条规则。例如可见性通常 6–7 条，单条 37.5/7≈5.36 分（看板显示 5.4）；规范通常是 18–21 条，单条约 1.79–2.08 分（看板显示 1.8–2.1）。报告里的「单条满分」一列给出整批的浮动区间。

`pending` 只扣一半分值；`na` 不扣分也不占分母。因此「某项不适用」会让其余规则的单条分值变高，而不是自动得满分。

### 1.3 总分相加（固定 100 分）

```text
每个维度 score = round(该维度权重 × ratio, 1)，不适用维度 score = 0.0
total = round(target + visibility + spec, 1)
三个维度权重之和恒为 25 + 37.5 + 37.5 = 100
```

也就是说，不适用维度按 0 分留在 100 分里，剩余维度不会被放大到 100 分制。
页面上的维度分相加严格等于总分；要让目标语义拿分，必须在 `expectations.json`
里把声明字段的 provenance 置为 `explicit`。

### 1.4 目标语义封顶

当同时满足以下三条时：

1. `oracle.gate` 为真（显式期望允许门禁）；
2. 目标语义维度适用；
3. 目标语义维度通过率 `< 100%`（有任何一条目标规则不是 pass）；

总分强制 `total = min(total, 59.9)`，结论附注「目标语义未通过，总分封顶 59.9」。目的是避免「样式好看但日期/关系文案错误」的卡片拿到及格以上。

### 1.5 L0 失败置零

只要结果中存在任一 `L0.*` 规则且取值为 0（fail）：

- 三个维度全部标记为不适用，原因「L0 失败」；
- 三个维度分数均为 0.0；
- `total = 0.0`，`fatal = true`，`availableWeight = 100`（固定总分基数）。

当前实际会产出的 L0 失败有两类：产物缺失（`L0.ARTIFACT_MISSING`）与浏览器采集失败（`L0.CAPTURE_FAILED`）。注意只要原始或注入任一版本采集失败，就会产生 `L0.CAPTURE_FAILED`，整卡 0 分。

### 1.6 分数等级

| 总分 | 等级 |
|---|---|
| ≥ 90.0 | 优秀 |
| ≥ 75.0 | 良好 |
| ≥ 60.0 | 及格 |
| < 60.0 | 不合格 |

### 1.7 样本状态与结论（与分数是两套口径）

状态只看规则状态与严重级别，不看分数：

- `failed`：存在 `severity = major` 的 fail；
- `partial`：存在任意 fail 或 pending，但没有 major fail；
- `success`：其余情况。

结论按以下优先级取第一个命中的：

1. 有 major 的 `L0.*` 失败 → 「L0 失败」；
2. 有 major 的 `TARGET.*` 失败 → 「目标语义失败」；
3. 有 major 的 `VIS.*` 失败 → 「可见性失败」；
4. 有 major 的 `SPEC.*` 失败 → 「规范失败」；
5. 仅有 minor fail 或 pending → 「待复核」；
6. 无失败但目标语义未计分 → 「通过（数据语义仅参考）」；
7. 无失败但目标语义未门禁 → 「通过（目标语义未门禁）」；
8. 其余 → 「通过」。

**严重级别不参与扣分**：`severity` 只影响样本状态与结论。一个 major 失败和 minor 失败，在维度分里扣的是同一个 `unit`；minor 失败不会让样本变成 `failed`，但会实实在在扣分，并使结论落到「待复核」。

### 1.8 精度

- 维度分、总分、单条扣分都保留 1 位小数；
- 总分是三个维度分（已各保留 1 位小数）的直接相加，单条扣分另做四舍五入，因此「逐条扣分相加」与「维度扣分」可能有 ±0.1 的显示差；
- 同一维度下所有规则的平均得分，其和约等于该维度整批平均分（报告口径，保留 1 位小数）。

## 二、参与计分的规则集合

### 2.1 目标语义（25 分）

目标语义**不按 `TARGET.` 前缀全收**，只收 `oracle.fields` 中声明、且能映射到卡面字段的三条：

| 字段 | 对应计分规则 |
|---|---|
| `days` | `TARGET.DAYS_MISMATCH` |
| `relationText` | `TARGET.RELATION_TEXT_MISMATCH` |
| `targetDateText` | `TARGET.VISIBLE_EXPECTATION_MISSING` |

- `targetDate` 只是工具入参，不参与比对。
- `fields` 为空时目标维度不适用（即使 provenance 全是 explicit）。
- 字段声明了但绑定缺失时，该字段按 0 分计入（见 §3.2 的 `TARGET.BINDING_MISSING`）。
- 其余 `TARGET.*`（占位文案、场景规则、绑定值变化、Oracle 为空）只在失败明细出现，**不参与目标分**。

### 2.2 可见性（37.5 分）

所有 `VIS.*` 规则等权计分，当前最多 8 条、常见 7 条（缺截图或 Pillow 时对比度为不适用）：

`VIS.TEXT_CLIPPED`、`VIS.TEXT_OVERFLOW`、`VIS.IMAGE_OVERFLOW`、`VIS.TEXT_OVERLAP`、`VIS.IMAGE_LOAD_FAILED`、`VIS.FONT_TOO_SMALL`、`VIS.CONTRAST_LOW`、`VIS.EVIDENCE_MISSING`。

rubric v3 起，同一根因只扣一次：被判定为其他规则派生症状的项会改为 `na` 并退出分母，
所以可见性实际适用条数可能少于 7 条（见 §3.5.1）。

### 2.3 规范符合（37.5 分）

所有 `SPEC.*` 中**排除诊断项**后等权计分。当前可有 21 条：

`RADIUS`、`CLIP`、`PADDING`、`BG_FULL_BLEED`、`BG_SINGLE`、`MASK`、`TITLE_REQUIRED`、`TITLE_FONT`、`TITLE_ELLIPSIS`、`TITLE_COLOR`、`PRIMARY_FONT`、`PRIMARY_COLOR`、`UNIT_FONT`、`UNIT_COLOR`、`SUPPORT_FONT`、`SUPPORT_COLOR`、`CONTENT_TYPE`、`PATTERN_GEOMETRY`、`DIGIT_LIMIT`、`ACTION_PATTERN`、`SAFE_AREA`。

其中 `SAFE_AREA` 来自 DOM 证据，其余来自 A2UI 组件树。

### 2.4 只诊断、不参与计分

以下规则会出现在规则表与样本明细中，但被评分器显式排除：

| 规则 | 原因 |
|---|---|
| `SPEC.THEME_ELIGIBLE` | 主题路线判定，只解释规范维度是否适用 |
| `SPEC.USER_PREFERENCE` | 记录用户偏好豁免了哪些项 |
| `SPEC.ICON` | 图标规格证据不稳定，只诊断 |
| `SPEC.BG_FIT` | 背景 fill/cover 只诊断，不判失败 |
| `SPEC.PATTERN_PITCH` | 图案间距只诊断，偏离记不适用 |
| `SPEC.UNIT_BASELINE` | 数字与单位基线只诊断 |
| `LAYOUT.CARD_OVERFLOW` | 卡片越界诊断，2026-11-11 新增 |
| `LAYOUT.PARENT_CLIP` | 中间容器裁切诊断，2026-11-11 新增 |
| `LAYOUT.SIBLING_OVERLAP` | 兄弟节点遮挡诊断，2026-11-11 新增 |
| `ASSET.FILE_MISSING` | 本地素材文件存在性，只诊断 |
| `ASSET.RENDERED` | 本地素材是否真实绘制，只诊断 |

### 2.5 已声明但当前不会产出

`RULE_ORDER` / `RULE_TITLES` 中存在，但代码里没有任何地方生成：

- `L0.RESULT_STATUS`（样本执行状态）
- `L0.PARSE_FAILED`（A2UI 解析失败，实际用 `L0.ARTIFACT_MISSING` 表达）
- `TARGET.ARGUMENT_MISMATCH`（工具参数与期望一致）

它们在规则表里会显示 0 次通过/失败，属于预留位。

## 三、逐规则明细

> 表中「扣分」列的含义：**计分** = 计入对应维度，单条分值 = 维度权重 ÷ 该样本适用条数；**否** = 只展示不扣分。所有 fail 扣满 `unit`，pending 扣 `unit × 0.5`。

### 3.1 L0 前置条件（失败即总分 0）

| 规则 | 触发条件 | 状态 | 扣分 | 看板原因 | 来源 |
|---|---|---|---|---|---|
| `L0.ARTIFACT_MISSING` | 无最终尝试目录；缺少 `genui.jsonl`；解析不到 A2UI 组件；缺少 `sample_static.json` 或 oracle | fail（major） | 总分归零 | 「存在可渲染的最终卡片产物」未满足，明细里给出具体缺失项 | 工程前置检查（`plugin.py`） |
| `L0.CAPTURE_FAILED` | 原始或注入版本渲染失败、采集超时、缺少 `target_capture.json` | fail（major） | 总分归零 | 「浏览器采集成功」未满足，明细给出 original/injected 的失败原因 | 采集链路（`capture_target_effect.mjs`） |
| `L0.RESULT_STATUS` | 声明但未实现 | — | — | — | 预留 |
| `L0.PARSE_FAILED` | 声明但未实现 | — | — | — | 预留 |

### 3.2 目标语义（25 分）

| 规则 | 通过条件 | 失败 / 待复核条件 | 扣分 | 看板原因 | 来源 |
|---|---|---|---|---|---|
| `TARGET.DAYS_MISMATCH` | 声明字段 `days` 的绑定路径被组件引用，且绑定叶子节点文本或整卡可见文本包含期望数字；数字按整数边界匹配（`198` 不会命中 `1980`） | 未匹配 → fail | 是（25/适用条数，通常 8.3） | 「卡片显示的天数与期望天数一致」 | `te_dom._target_results`；期望来自 `te_oracle.py` |
| `TARGET.RELATION_TEXT_MISMATCH` | 可见文本包含期望关系文案（`还剩` / `已过` / `就是今天`） | 未包含 → fail | 是 | 「关系文案与日期差方向一致」 | 同上 |
| `TARGET.VISIBLE_EXPECTATION_MISSING` | 可见文本包含期望日期文本；支持 `YYYY/MM/DD` 精确匹配，以及 `YYYY-MM-DD`、`YYYY.MM.DD`、`YYYY年MM月DD日`、`M/D`、`M月D日` 变体 | 全部变体都不出现 → fail | 是 | 「注入的期望文本在卡片上真实可见」 | 同上 |
| `TARGET.BINDING_MISSING` | `writeResultTo/字段` 被至少一个组件引用；全部引用时产出 1 条 pass | 某字段无人引用 → 每字段 1 条 fail | **否**（但会使对应字段按 0 分计入） | 「期望字段被组件引用，而不是写死文本」 | 同上 |
| `TARGET.BINDING_VALUE_MISMATCH` | 注入期望后，绑定节点文本发生变化且包含期望值 | 原始文本为空，或注入前后文本相同且不含期望值 → fail | 否 | 「注入值变化时，卡片文本随之变化」 | `te_dom._binding_update_results` |
| `TARGET.PLACEHOLDER_VISIBLE` | 可见文本非空且不含占位文案 | 出现 `待同步/待确认/暂无数据/暂无记录/加载中/placeholder` → pending | 否 | 「卡片上不出现占位文案」 | `te_dom._placeholder_results` |
| `TARGET.SCENARIO_RULE_VIOLATION` | 仅当目标门禁开启且期望关系文案属于三种关系词；命中期望 → pass | 未命中期望却出现其他关系词 → fail；都没有 → 不产出 | 否 | 「场景规则成立」 | `te_dom._scenario_results` |
| `TARGET.ORACLE_EMPTY` | — | 门禁开启但没有任何可推导期望 → na | 否 | 「可推导的期望值」 | `te_dom._target_results` |
| `TARGET.ARGUMENT_MISMATCH` | 声明但未实现 | — | — | — | 预留 |

**期望值从哪里来（决定目标维度是否适用）：**

1. 从请求的 `candidateDataBindings` 中取 `capabilityId = GetDateCounter` 的绑定，读取 `arguments.targetDate`、`repeat`、`writeResultTo`、`candidateOutputFields`；
2. 参考日期取 `deviceInfo.time` 前 8 位（`YYYYMMDD`），按 `Asia/Shanghai` 语义处理日期；
3. 一次性倒计时：目标日即 `targetDate`，`days = |目标日 − 参考日|`，关系文案按差值正负零取「还剩 / 已过 / 就是今天」；
4. 重复场景：按周/月/年/天推下一次触发日；`repeatGates` 默认关闭，推导结果只展示；农历场景不自动判定；
5. 数据集作者可用运行目录下的 `expectations.json`（或配置 `expectationsPath`）覆盖期望值；只有其 `provenance` 中出现的字段全部为 `explicit`，目标维度才适用。

**典型口径：** 当前仓库的批跑没有 `expectations.json`，provenance 为 `derived`，所以 `target_applicable` 为假，目标维度 `checks = 0`、`applicable = false`，25 分权重从分母中剔除。

### 3.3 可见性（37.5 分）

证据来源：`dom_injected.json` 中的 `webQuality.findings`（`collectWebQuality`）与 DOM 节点样式；对比度额外采样 `injected.png`。

| 规则 | 通过条件 | 失败 / 待复核条件 | 扣分 | 看板原因 | 来源 |
|---|---|---|---|---|---|
| `VIS.TEXT_CLIPPED` | 没有横向 `GEOMETRY.CLIP_TEXT` | 文本矩形被 `overflow: hidden/clip` 祖先横向裁掉，或 `ellipsis`/`line-clamp` 触发且 `scrollWidth > clientWidth + 2` → fail；只有纵向行框溢出（`scrollHeight` 超出而宽度未超）视为字体 leading，**不计失败** | 是 | 「文字没有被容器横向裁切」 | `web_quality.mjs` → `te_dom._web_quality_results` / `te_dom._is_horizontal_clip` |
| `VIS.TEXT_OVERFLOW` | 没有 `GEOMETRY.OVERFLOW_TEXT` | 文本矩形超出卡片画布（容差 2px）→ fail | 是 | 「文字没有越出卡片边界」 | 同上 |
| `VIS.IMAGE_OVERFLOW` | 没有 `GEOMETRY.OVERFLOW_IMAGE` | 图片矩形超出卡片画布 → fail | 是 | 「图标或图片没有越出卡片边界」 | 同上 |
| `VIS.TEXT_OVERLAP` | 没有 `GEOMETRY.OVERLAP_TEXT` | 两个独立文字区域矩形相交超过 2px → **pending**（字形级遮挡待人工确认） | 是（扣一半） | 「文字之间没有互相遮挡」 | 同上 |
| `VIS.IMAGE_LOAD_FAILED` | 没有 `ASSET.WEB_LOAD_FAILED` | 图片 `naturalWidth = 0`、加载未完成，或 alt 以「素材未找到」开头 → fail | 是 | 「图片资源在渲染时真实加载成功」 | 同上 |
| `VIS.FONT_TOO_SMALL` | 所有可见叶子文本字号 ≥ 12 | 任一节点字号在 (0, 12) → **pending**；若这些节点已被失败的 `SPEC.*_FONT` 完全覆盖，则改为 `na`，不重复扣分 | 是（扣一半） | 「正文字号不低于可读下限」 | `te_dom._font_results` + `plugin._dedupe_results` |
| `VIS.CONTRAST_LOW` | 采样节点对比度 ≥ 阈值 × 0.9（普通阈值 4.5、大字阈值 3） | 背景纹理方差 > 42 → **pending**（需人工复核）；否则对比度 < 阈值 × 0.9 → fail。若 `SPEC.MASK` 失败，或对比度低的节点已被失败的配色规则完全覆盖，则改为 `na` | 是 | 「正文对比度不低于 4.5:1，大字不低于 3:1」 | `te_dom._contrast_results`（WCAG 相对亮度公式）+ `plugin._dedupe_results` |
| `VIS.EVIDENCE_MISSING` | 有完整 `webQuality` 证据 | 缺 `webQuality`，或整个 DOM 证据缺失 → **pending** | 是（扣一半） | 「DOM 与截图证据完整，能支撑可见性判定」 | `te_dom._web_quality_results` / `plugin.py` |

对比度实现细节：

- 取节点 `box` 在截图中的对应区域，按截图宽高与画布 CSS 宽高推算横纵倍率；
- 用区域内像素亮度的中位数把像素分成亮/暗两堆，取数量较多的一堆估算背景色；
- 前景色用节点 `color`，按 alpha 与背景做合成；
- 「大字」判定：字号 ≥ 24，或字号 ≥ 18.66 且字重 ≥ 700；
- 背景纹理复杂（亮度标准差 > 42）时不判失败，记 pending；
- 找不到截图、缺少 Pillow、色值无法解析、区域小于 6×6 时跳过该节点；全部跳过则不产出该规则（不占分母）。

### 3.4 规范符合（37.5 分）— 基于 A2UI 组件树

来源：[倒计时卡片规范.md](/D:/down/倒计时卡片规范.md)（Pixso 源文件逐节点解析，1x 设计稿实测），以及 `te_spec.py` 头部记录的 rubric v2 决策与 v3 去重口径。

| 规则 | 通过条件 | 失败 / 不适用条件 | 扣分 | 看板原因 | 规范来源 |
|---|---|---|---|---|---|

### 3.5.1 同因去重（rubric v3）

同一根因只扣一次。被去重的项改为 `na`，退出该维度分母，并在 `evidence.dedupe`
里留下 `{"from": 原状态, "to": "na", "reason": 去重原因}`，明细仍可复核。

| 症状规则 | 根因规则 | 去重条件 | 实现位置 |
|---|---|---|---|
| `VIS.TEXT_CLIPPED` | `SPEC.TITLE_ELLIPSIS` | 裁切只发生在标题/副标题，且省略号规则已失败 | `plugin._dedupe_one` |
| `VIS.CONTRAST_LOW` | `SPEC.MASK` | 蒙层失败，背景亮度本身错误 | `plugin._contrast_root_cause` |
| `VIS.CONTRAST_LOW` | `SPEC.TITLE_COLOR` / `PRIMARY_COLOR` / `UNIT_COLOR` / `SUPPORT_COLOR` | 对比度偏低节点被失败的配色规则完全覆盖 | `plugin._covered_by` |
| `SPEC.PADDING` | `SPEC.SAFE_AREA` | 两条同时失败，同一 12vp 边距 | `plugin._dedupe_one` |
| `VIS.FONT_TOO_SMALL` | `SPEC.TITLE_FONT` / `PRIMARY_FONT` / `UNIT_FONT` / `SUPPORT_FONT` | 过小节点被失败的字号规则完全覆盖 | `plugin._covered_by` |
| `SPEC.SAFE_AREA` | `VIS.TEXT_OVERFLOW` | 越界文本已由溢出规则计分（按节点排除） | `te_dom._safe_area_results` |
| `VIS.TEXT_CLIPPED` | 行高 leading | `scrollWidth ≤ clientWidth + 2` 且文本矩形未横向超出自身盒子 | `te_dom._is_horizontal_clip` |

「完全覆盖」按节点 id 判断：对比度/字号症状涉及的节点必须全部出现在失败根因规则的证据里
才去重；只要还有一个未被覆盖的节点，症状规则仍照常扣分，避免把独立问题一起豁免。

### 3.5.2 标题未溢出豁免（DOM 证据）

规范只要求「超出最大宽度时单行截断并加省略号」，声明缺失但实际没有溢出的短标题不扣分：

- 只对 `SPEC.TITLE_ELLIPSIS` 的失败项生效；
- 失败项声明的每个标题/副标题，都必须在 `target-dom-v2` 证据里满足：`visible` 不为 false、
  非 `zeroSized`、`lineCount ≤ 1`、`scrollWidth ≤ clientWidth + 2`，且 `renderedText`
  与 `text` 完全一致（证明没有被裁切）；
- 满足时改记 `na`，`evidence.dedupe.reason` 为「标题未溢出，省略号不影响显示」；
- 任一标题不满足（换行、横向溢出、被裁切、缺 v2 字段）则整条保持失败；
- `target-dom-v1` 证据没有 `lineCount/clientWidth/scrollWidth/renderedText`，无法豁免，
  旧样本需重新采集后才生效。

实现：`plugin._waive_title_ellipsis`，在 DOM 结果并入后、同因去重前执行。

| 规则 | 判定 | 说明 |
|---|---|---|
| `SPEC.THEME_ELIGIBLE` | 主题登记表条目为 `photo`、有背景图、`content.roles.primary` 为 ≥90% 白 → pass；登记为非 Pixso 路线 → na；主题未登记 → 按图+蒙层路线评估 | 决定规范维度是否「应当」适用，但见 §5.2 |

三条 `LAYOUT.*` 只在 `target-dom-v2` 证据上运行；旧证据直接跳过。它们是 pending 诊断，
不会让样本变成待复核，也不进入任何维度分母。

**用户偏好豁免：** 用户原话命中关键词时，相关规范项从计分集合中移除（记为 na）：

- 背景/底色/蒙层/纯色/渐变/透明 → 豁免 `BG_FULL_BLEED`、`BG_SINGLE`、`BG_FIT`、`MASK`；
- 颜色词/配色/颜色 → 豁免 `TITLE_COLOR`、`PRIMARY_COLOR`、`UNIT_COLOR`、`SUPPORT_COLOR`；
- 字号/字体大小/大字/小字/加粗/字重 → 豁免 `TITLE_FONT`、`PRIMARY_FONT`、`UNIT_FONT`、`SUPPORT_FONT`。

豁免是「整条移除」，不是改判通过：分母变小、其余规则分值变高。

## 四、计算示例

### 4.1 典型样本（无显式期望）

以 2026-11-11 的 `batch_20261110_200000_7e5a1b2c` 为例：6 个样本，目标维度全部不适用
（provenance 为 `derived`），可见性 6 条，规范 17–19 条。

Q001（2x2），rubric v4 固定 100 分口径（实测，不是推算）：

- 目标语义：不适用 → 0.0/25；
- 可见性：6 条全部通过 → 37.5/37.5；
- 规范符合：19 条中 12 条通过 → ratio = 12/19 = 63.2% → 23.7/37.5，单条 `37.5/19 ≈ 2.0`；
- 总分 = 0.0 + 37.5 + 23.7 = **61.2** → 等级「及格」；
- 因为目标维度不适用，不触发封顶，也不加「目标语义未通过」附注。

其余 5 个样本的 v4 实测分别为 61.2、59.6、61.2、60.4、63.2，平均 61.1。
同一批数据按旧的「(可见性 + 规范) ÷ 75 × 100」口径会显示 81.6、79.5、81.6、80.5、84.3
（平均 81.5），差额来自旧口径把未获得的目标 25 分按 75 分基数重新放大。
三条 `LAYOUT.*` 诊断在该批均未触发。

### 4.2 显式期望且目标失败（封顶示例）

假设三条目标规则中只有 `days` 失败，可见性与规范全部满分：

- 目标：2/3 → 得分 16.7；
- 可见性：37.5；
- 规范：37.5；
- 总分 = 16.7 + 37.5 + 37.5 = 91.7；
- 因目标适用且 ratio < 100%，封顶为 **59.9**，等级「不合格」，附注「目标语义未通过，总分封顶 59.9」。

### 4.3 L0 失败

任一版本采集失败：

- 三个维度全部不适用，`total = 0.0`，`fatal = true`；
- 样本状态 `failed`，结论「L0 失败」；
- 看板的失败明细会给出 `L0.CAPTURE_FAILED` 的 original/injected 具体原因。

## 五、复核重点与已知口径问题

以下按「实际代码行为」列出，供逐项确认是否需要调整。

### 5.1 严重级别不参与扣分

`severity` 只用于样本状态/结论。`SPEC.RADIUS`、`SPEC.CLIP`、`SPEC.TITLE_COLOR` 等标为 minor 的规则，一旦失败仍扣满单条分值（规范维度里约 1.9 分），只是不会把样本判成 `failed`。如果希望 minor 扣半或只提示，需要另加权重字段。

### 5.2 非 Pixso 主题仍可能被 `SPEC.SAFE_AREA` 计分

文档写的是「非 Pixso 主题规范维度整维不适用」，但实际链路是：

1. `evaluate_spec` 在主题不合格时只返回 `SPEC.THEME_ELIGIBLE`（诊断项）；
2. `evaluate_dom` 仍会产出 `SPEC.SAFE_AREA`（计分项）；
3. 评分器看到 `SPEC.SAFE_AREA`，于是规范维度**仍然适用**，且只剩这一条规则，其单条满分变成 37.5。

实测：只给 `SPEC.THEME_ELIGIBLE = na` 和 `SPEC.SAFE_AREA = pass` 时，规范维度得分 37.5/37.5、`applicable = true`。也就是说，非 Pixso 主题的样本会仅凭「文字在安全区内」拿满规范 37.5 分。是否要把 `SAFE_AREA` 也随主题豁免，需要确认。

另外，rubric v4 固定 100 分后，如果主题不合格且没有任何计分 `SPEC.*` 规则，规范维度会记 0/37.5，样本最高只能拿 62.5 分。这与「非 Pixso 主题不做规范门禁」的原意冲突；是否改为「主题不合格时整维不参与 100 分」需要确认。

### 5.3 分母随样本浮动，单条分值不固定

同一条 `SPEC.TITLE_FONT`，在规范 20 条适用的样本里值 1.9 分，在 15 条适用的样本里值 2.5 分。报告已经用「单条满分」区间提示，但**跨样本比较单条扣分时要看区间，不能按固定分值理解**。

### 5.4 同一规则多条结果取平均

`_prefix_checks` 对同名规则的所有结果取算术平均。`TARGET.BINDING_MISSING` 在字段缺失时会对每个缺失字段各产出一条 fail，另有一条「全部字段引用」的 pass；但该规则本身不参与目标分，所以这个平均只影响展示，不影响分数。目标分只由三条映射规则决定。

### 5.5 mock 推导的期望不计分，但会影响字体档位

目标维度依赖 `provenance = explicit`；当前批跑没有 `expectations.json`，所以 `expectedDays` 只作参考。但 `SPEC.PRIMARY_FONT` 和 `SPEC.DIGIT_LIMIT` 仍会使用推导出的 `oracle.days` 判断「长数字 29–56」和「最多 6 位」。因此 mock 日期会间接影响规范分，只是不会以「目标语义」名义扣分。

### 5.6 `gate` 与「目标维度适用」不是同一件事

一次性倒计时会让 `oracle.gate = true`（允许门禁），但 `days/relationText/targetDateText` 的 provenance 仍是 `derived`，`target_applicable` 为假，目标维度记 0/25、也不封顶。只有 `expectations.json` 把声明字段的 provenance 置为 `explicit`，目标分才会参与。历史执行 `exec_ff13cef898d2`（插件 1.0.0）曾按 gate 计目标分，同一批样本总分 77.3；插件 1.3.0 同批为 65.8（两者均为旧权重 25/25 口径），属于口径升级，不是数据变化。

### 5.7 声明但未实现的三条规则

`L0.RESULT_STATUS`、`L0.PARSE_FAILED`、`TARGET.ARGUMENT_MISMATCH` 只在规则表与标题映射里存在，不会产出结果；规则表会显示 0 次。若希望「样本本身执行失败」单独成规则，需要补实现，而不是依赖 `L0.ARTIFACT_MISSING`。

### 5.8 `L0.CAPTURE_FAILED` 不在规则汇总表

`RULE_ORDER` 没有收录 `L0.CAPTURE_FAILED`，所以整批「细分维度平均」表里看不到它的通过/失败统计；但样本 `results`、失败明细和结论都会包含它，且它会触发总分归零。

### 5.9 用户偏好关键词是「出现即豁免」

只要用户原话里出现「背景」「纯色」「渐变」「颜色」「字号」等词，就会豁免整组规范项。像「**不要**纯色背景」「颜色要**鲜艳**」这类否定/修饰语境也会命中，导致相关规范项不扣分。当前没有否定词判断。

### 5.10 蒙层 alpha 可能被双重衰减

`SPEC.MASK` 用「色值 alpha × `opacity`」计算有效透明度。如果 DSL 同时写了 `#99000000`（60% 黑）和 `opacity: 0.6`，有效 alpha 会变成 0.36，低于 0.55 判失败。规范只要求 60% 黑；是否应对这种写法做兼容，需要确认。

### 5.11 标题字号不区分 T1–T4

规范里 T1/T2 用 16fp、T3/T4 用 20fp；当前 `SPEC.TITLE_FONT` 只要求「主标题 16 或 20，副标题 16」，不校验变体与字号是否配对。20fp 主标题配 16fp 副标题会通过，即使实际版式是 T1。

### 5.12 单位必须独立成节点

规范 §4.1 和 §8 的示例写法是「还剩 6 天」这类合并文案，但 rubric v2 起要求单位独立 16fp。当前 `SPEC.UNIT_FONT` 对「数字与单位同一文本节点」直接判失败（major），即使字号是 16。这是 rubric 决策与规范示例表述之间的冲突点，建议确认口径。

### 5.13 `SPEC.SAFE_AREA` 只看文本

安全区规则使用「可见且有文本的叶子节点」，不覆盖图片、纯装饰节点。图片越界只由 `VIS.IMAGE_OVERFLOW` 检查画布边界（不是 12 内边距）。也就是说，图片可以压到 12 边距内但仍在画布内而不被规范扣分。

### 5.14 背景/图案识别依赖精确像素与 `matchParent`

- `SPEC.BG_FULL_BLEED` 只认 `width = height = "matchParent"` 的 Image；数值宽高（如 150）不算满铺。`title_icon` 被排除，但其他 `matchParent` 装饰图会被当成背景图，可能触发 `BG_SINGLE`「多张满铺图」失败。
- `SPEC.PATTERN_GEOMETRY` 只认 `10×60` 柱体和 `8×8` 圆球；用其他节点表达的图案会被判「非图案类」而 na。
- 尺寸只有 `2x2` / `2x4` 两档；其他 `size` 值会回落到 2x2 的柱体/圆球数量。

### 5.15 Web 采集的边界

可见性与对比度来自 Chromium 对本地预览页的排版，不是鸿蒙端侧 Form 的真实排版。字体回退、行高换算、系统字体缩放都可能有差异。当前结论只应视为「Web 渲染证据」，不能直接当端侧通过结论。

另外，`webQuality.complete`（画布尺寸与测量数量是否有效）没有被评分器检查：即使画布为空、`complete = false`，只要 `findings` 为空，五条映射规则仍会全部记通过。

### 5.16 对比度启发式的已知限制

- 背景色用「亮/暗两堆中数量较多者」的均值估算；文字占区域比例较高时可能把文字像素当成背景，导致比值偏低或偏高；
- 纹理方差 > 42 记 pending，不判失败；
- 节点区域小于 6×6、色值不是 `rgb()/rgba()`、缺截图或缺 Pillow 时跳过；若所有节点都被跳过，该规则不产出（不占分母，等于不扣分）。

### 5.17 当前 6 个样本的共性问题

`exec_ba1953a1567e` 的 6 个样本全部（旧权重 25/25 口径）：可见性 17.9（`TEXT_CLIPPED` + `CONTRAST_LOW` 失败）、规范分 13.9–16.2。`SPEC.MASK`、`TITLE_FONT`、`TITLE_ELLIPSIS`、`TITLE_COLOR`、`UNIT_FONT`、`SUPPORT_FONT`、`SUPPORT_COLOR` 在 6 个样本里全部失败，`SPEC.PRIMARY_FONT` 失败 5 个。若认为这些是数据侧问题，可先按样本核对；若认为规则过严，优先复核 `SPEC.MASK` 的黑色层识别与对比度采样。
